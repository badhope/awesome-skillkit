# Database migrations

AI-SKILL uses [Alembic](https://alembic.sqlalchemy.org/) for schema
migrations. All schema changes **must** go through a migration —
never run `CREATE TABLE` by hand in production.

## Workflow

1. Edit the model in `backend/app/models/skill.py` (or a sibling
   file).
2. Autogenerate a migration:
   ```bash
   cd backend
   poetry run alembic revision --autogenerate -m "add skill_versions table"
   ```
3. **Review** the generated file in
   `backend/alembic/versions/`. Alembic is conservative; it will
   miss things like column renames and enum value changes.
4. Apply locally and test:
   ```bash
   poetry run alembic upgrade head
   poetry run pytest
   poetry run alembic downgrade -1    # smoke-test the downgrade
   poetry run alembic upgrade head
   ```
5. Commit and push.
6. The CI workflow runs `alembic upgrade head` against a fresh
   database to verify the migration is repeatable.

## Naming

Migrations live in `backend/alembic/versions/` and follow the
pattern:

```
<sequence>_<short_slug>_<description>.py
```

The sequence is global — `0001`, `0002`, `0003`, …

Examples:

- `0001_initial.py`
- `0002_add_skill_versions.py`
- `0003_add_analytics_events.py`

The autogenerated filename will be in the right shape; you usually
do not need to rename.

## What autogenerate catches

| Change                                       | Autogenerate? |
|----------------------------------------------|---------------|
| Add / drop a column                          | Yes           |
| Add / drop a table                           | Yes           |
| Add / drop an index                          | Yes           |
| Change a column type                         | Sometimes     |
| Rename a column                              | **No** (treated as drop + add) |
| Rename a table                               | **No** (treated as drop + add) |
| Change a `ForeignKey` constraint             | Sometimes     |
| Add / drop a check constraint                | Yes           |
| Add / drop a `UniqueConstraint`              | Yes           |
| Change a default value                       | Sometimes     |

If in doubt, **edit the migration by hand**. Alembic is just a thin
wrapper around SQL; you can put any SQLAlchemy DDL in `op.execute()`.

## Dangerous migrations

### Dropping a column

Alembic will drop the column on `upgrade`. On `downgrade`, the data
is gone. For destructive changes:

1. Stop the backend.
2. Take a database snapshot.
3. Apply the migration.
4. Smoke-test.
5. Keep the snapshot for 7 days before pruning.

### Adding a NOT NULL column without a default

This will fail if the table has rows. Either:

- Add the column nullable, backfill with a script, then set NOT NULL
  in a follow-up migration.
- Or add the column with a server-side `DEFAULT`.

### Renaming a column

Alembic treats a rename as drop + add, which **destroys data**. The
right pattern is:

```python
def upgrade() -> None:
    op.alter_column("skills", "old_name", new_column_name="new_name")

def downgrade() -> None:
    op.alter_column("skills", "new_name", new_column_name="old_name")
```

### Adding a CHECK constraint

The autogenerator will add it without validating existing rows. For
a large table, run with `postgresql_using="VALIDATE CONSTRAINT"`
in a separate transaction after the data has been backfilled.

## Production deployment

Migrations are applied **automatically** by the backend on startup
(via the FastAPI `lifespan` hook). The deploy pipeline:

1. Build the new backend image.
2. Start the new container.
3. The container runs `alembic upgrade head` inside the entrypoint.
4. The Gunicorn / uvicorn process only starts once the migrations
   complete.

If a migration fails, the new container exits and the rolling
update pauses. The previous version is still serving traffic. Fix
the migration, push a new image.

## Rolling back a migration

In a pinch:

```bash
# Connect to the running backend
docker compose exec backend poetry run alembic downgrade -1
```

This is **not** a substitute for fixing forward. After a rollback,
add a new migration that performs the inverse operation so the
schema is back in sync with the models.

## Seed data

Migrations are for **schema**, not data. The `app.core.seed`
module seeds categories, tags, and the first admin. It is
**idempotent** — safe to run on every startup.

If you need to seed a specific fixture for a test, put it in
`tests/conftest.py`, not in a migration.
