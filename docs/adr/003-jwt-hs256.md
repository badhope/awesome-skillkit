# ADR 003 — JWT (HS256) over RS256

- **Status**: Accepted
- **Date**: 2026-06-01

## Context

We need a stateless, signed authentication token. The two main
choices are HMAC (HS256, single shared secret) and RSA / ECDSA
(RS256 / ES256, public / private key pair).

## Decision

Use **HS256 with a single shared secret** for v1.

## Rationale

- Single self-hosted service — there is no second service that
  needs to verify tokens without holding the signing key.
- HS256 is faster, simpler, and easier to rotate.
- Refresh-token rotation is supported by the existing
  `/auth/refresh` flow. The previous description of a
  Redis-backed JTI denylist was **aspirational and not yet
  implemented** (as of the date on this ADR).

## When to revisit

If we add a separate "agent runner" or "edge worker" service that
must verify tokens without holding the signing key, we will move to
RS256 and publish the public key in a JWKS endpoint.

## Consequences

- The signing key (`JWT_SECRET_KEY`) is the single most important
  secret in the system. Production refuses to start without a
  32+ char key.
- The key is loaded once at process start; rotation requires
  coordinated restart of all backend replicas.
